# PokeHunt Analytics — plano de implementação

**Objetivo:** entregar o analisador local completo descrito no briefing fornecido pelo usuário.
**Arquitetura:** Next.js App Router com exportação estática. Validação, normalização e cálculos são funções puras independentes da interface. O componente cliente mantém o JSON e a análise somente em memória.
**Stack:** TypeScript, Tailwind, shadcn/ui, Recharts, Lucide.
**Especificação:** `docs/briefing.md` (texto integral fornecido pelo usuário).

## Restrições

- Sem backend, login, armazenamento persistente, telemetria ou envio do JSON.
- Session sempre prevalece, inclusive quando informa zero; valores indisponíveis são null.
- Divisões por zero ou resultados não finitos não são exibidos.
- Não associar drops a criaturas nem inventar métricas ausentes.
- Novos campos são tolerados, campos conhecidos inválidos recebem erro com localização.

## Direção visual

Grafite #0c0f14, superfície #141920, borda #29303a, texto #edf1f5, azul mineral #82c8d5. Verde/vermelho apenas para resultados e dourado para raros. Manrope para interface e IBM Plex Mono para dados, ambos locais. Marca geométrica de mira; assinatura visual: resumo financeiro como extrato compacto com cobertura dos gastos. Editor ocupa o centro da página inicial sem conteúdo promocional.

## Casos de aceite automatizados

Fixture obrigatória: profit -8203; loot 11436; supplies 19639; kills 344; XP 194023; duração 1769; dano causado 2341130 e recebido 272869. Remover Session testa fallback; manter Session com zero testa precedência. Agrupar registros repetidos por Enemy e Element testa dano. Ausência de arrays produz null; arrays vazios produzem zero. Fluxo E2E usa exemplo, navega cinco abas, ordena tabela, edita entrada inválida sem perder resultado e inicia nova análise. Interações não devem gerar requisições com dados da hunt.
